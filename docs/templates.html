Templates, bound and unbound

What a template is, and how the project’s one differs from the rest.

Shipped templates #

Barnark ships a catalogue of five: Domain Driven Design, Feature Based Architecture, Model View Controller, Library and Package App. They are read-only, and only a new Barnark changes them. The next page says what each is for.

Clone and copy #

Two commands turn a shipped template into yours, and both copy:

  • Clone copies a template under a name you give and makes the project’s folder to it, so the copy becomes the project’s template.
  • Copy only makes a new template of your own. It makes no folder. Any template can be copied: a shipped one, one of yours, or the project’s own, members included.

Either way the copy is tied to nothing. Changing it never changes the template it came from, and a later Barnark that changes a shipped template never reaches it. The name can’t be one the project already has, or a shipped template’s name, ignoring case.

$ vendor/bin/barnark template:copy Hotel "domain driven design"
Barn: …/hotel

 [ERROR] 'domain driven design' can't name a template: a shipped template is
         called 'Domain Driven Design'.

Bound and unbound #

A project has one folder and one template that follows it. That is the bound template, made together with its folder by a clone. Barnark records which folder it is bound to in .barn/barnark/tracked-folders.json, and keeps each of the project’s templates, with its revisions, in .barn/barnark/catalogue/.

The project’s other templates are unbound: ones you made by copying. An unbound template isn’t attached to any folder. It can be cloned into a project that has nothing bound, like a shipped template, or deleted. While a template is bound, another clone is refused.

$ vendor/bin/barnark template:clone Library Pricing ./lib
Barn: …/hotel

 [ERROR] The project has its template already: 'Hotel', bound to '/src'.

Note. Nothing unbinds the project’s template or removes its folder: ending a template’s life is not built yet.

The Keep templates of your own page shows copying, listing and deleting.

What is in a template #

A template is a tree of folders. Each folder in it is one of these:

  • Fixed folder. A folder the template names itself, such as Kernel in Domain Driven Design or Api in Library. Every folder made to the template has it.
  • Collection. A folder that holds only members, all of one member type, such as Context in Domain Driven Design.
  • Member. A folder you add to a collection and name, such as Reservation in Context.
  • Member type. What the template says once about every member of a collection: what a member is, and which folders it holds. Context’s member type is a bounded context, which holds Application, Domain, Infrastructure and PublicApi.

Each folder and each member type has a meaning, in words, that says what it is for. A folder with no folders of its own is a leaf: it is where the template stops and your code begins.

Adding a member copies its member type’s shape into the template as folders of the member’s own, so adding one is a change to the template and makes a revision. Because every member has the same shape as its member type, Barnark doesn’t let you add a folder inside a member, or change one member alone.

Note. The command line calls what a folder offers a slot: template:offers lists them and template:new takes one by name. A slot is a member type.

Tags #

A template can tag its folders, to say what part each plays. Domain Driven Design tags its layers: Application, Domain, Infrastructure and Transport. Package App tags each context’s Application and Infrastructure. A tag has a meaning, and a folder carries the tags of its kind of folder, so every context you add brings its layers’ tags. A folder the template has no place for carries none.

The browser app shows tags as coloured labels beside a folder’s name, and can pick one out so that you see only the folders that carry it and the folders above them, every context’s Application together, for instance.
